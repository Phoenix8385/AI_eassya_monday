# AI Essay Detector — backend

FastAPI service that scores an essay for AI-generated writing using GPT-2 token
perplexity, sentence-rhythm burstiness and stylistic features, then classifies
with a trained scikit-learn model. It returns per-sentence evidence, not a bare
percentage.

## Layout

```
backend/
  app/
    main.py                    FastAPI app, CORS, lifespan, /health, error handlers
    config.py                  Pydantic Settings — the only source of configuration
    routers/analyze.py         POST /analyze (thin: validate, delegate, return)
    services/model_loader.py   the ONE place GPT-2 + tokenizer are loaded
    services/signals.py        perplexity / burstiness / stylistic features (pure)
    services/classifier.py     loads the .joblib, scores, builds explanations
    services/rate_limit.py     in-memory sliding-window per-client limiter
    models/schemas.py          request/response models with field validation
    data/                      dataset CSVs + the trained classifier.joblib
  scripts/prepare_daigt.py        normalizes the Kaggle download
  scripts/build_polished_set.py   builds the AI-polished hard-case set
  scripts/train_classifier.py     regenerates app/data/classifier.joblib
  scripts/write_dataset_doc.py    generates DATASET.md
  scripts/generate_evaluation.py  generates EVALUATION.md
  requirements.txt             pinned, generated by `pip freeze`
  .env.example                 documented environment variables
```

## Setup

```bash
python -m venv venv
source venv/Scripts/activate        # Windows: venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env                 # then edit CORS_ORIGIN for your frontend
```

## Build the dataset

### 1. Base dataset — DAIGT competition data

```bash
pip install kaggle
kaggle auth login                # or set KAGGLE_API_TOKEN / ~/.kaggle/access_token
kaggle competitions download -c llm-detect-ai-generated-text
unzip llm-detect-ai-generated-text.zip -d app/data/raw

python -m scripts.prepare_daigt
```

You must accept the competition rules on the Kaggle website before the download
works — the API returns 403 until you do, even with valid credentials.

`prepare_daigt.py` prints the real columns of every CSV it opens and maps them
explicitly rather than assuming. The competition's three files do not share a
schema, and only one of them is labelled:

| File | Columns | Used |
|---|---|---|
| `train_essays.csv` | `id, prompt_id, text, generated` | ✅ text=`text`, label=`generated` |
| `test_essays.csv` | `id, prompt_id, text` | ❌ skipped — no labels |
| `train_prompts.csv` | `prompt_id, prompt_name, instructions, source_text` | ❌ skipped — not essays |

It then drops empty essays, exact and whitespace-only-differing duplicates, and
anything under 50 words (below that, burstiness and per-sentence perplexity are
too noisy to be worth anything), and writes `app/data/daigt_essays.csv` with
exactly `text, label` (0 = human, 1 = AI).

**Watch the class balance it prints at the end.** The competition's labelled
training file is heavily human-skewed, so raw accuracy is close to meaningless —
a model that always predicts "human" scores extremely well. Judge it on
per-class precision/recall and ROC-AUC, and keep `class_weight="balanced"` in
training. The script prints the exact ratio and warns above 3:1; record that
figure in `DATASET.md`.

### 2. Hard cases — AI-polished human essays

```bash
python -m scripts.build_polished_set --dry-run   # free, verifies the pipeline
python -m scripts.build_polished_set             # real run, costs money
```

Takes 40 human essays (`random_state=42`, so the sample is reproducible) and has
Claude polish each one. The output keeps a human's ideas, structure and voice
with only the surface machine-touched — the case a detector trained on
wholly-generated text will miss.

Three properties worth knowing:

- **Three rotating prompts, not one** (~13–14 essays each: light grammar/flow,
  sentence variety/word choice, grammar+phrasing keeping voice). One fixed
  prompt would make every polished essay a variation on a single instruction,
  clustering them tightly in feature space and making the evaluation look better
  than the real problem is. `prompt_variant` is stored per row so you can check
  later whether lighter polishing is harder to detect.
- **Resumable.** Each finished essay is appended to `app/data/polished_cache.jsonl`
  (keyed by source row index) and flushed before the next call starts. Re-running
  skips anything cached; `--resume-only` rebuilds the CSV with zero API calls.
- **Failures are logged, not fatal.** Up to 3 attempts with exponential backoff
  and jitter for rate limits, 5xx, timeouts and connection errors — honouring
  `retry-after` when the server sends it. 4xx errors and model refusals are not
  retried (they fail identically every time). Anything that exhausts its attempts
  goes to `app/data/failures.log` and the batch continues; re-run to retry only
  the failures.

Output is `app/data/ai_polished_essays.csv` with `text, original_text, label,
source, prompt_variant`. `original_text` is kept for manual spot-checking.

Credentials resolve from `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, or an
`ant auth login` profile. The client is built with `max_retries=0` on purpose —
the script owns retrying, and leaving the SDK's default of 2 in place would
multiply the two layers into up to 9 requests per essay instead of 3.

### 3. Document what you built

```bash
python -m scripts.write_dataset_doc      # -> DATASET.md
```

Reads both CSVs and writes `DATASET.md` with every count, percentage, ratio and
word-length statistic computed from the actual files. The prose (sources, scope
limitations, why the framing is probabilistic) is authored in the script's
templates; only the numbers are derived — so the document cannot drift out of
sync with the data. Re-run it after any dataset change.

It refuses to run if either CSV is missing rather than emitting a document with
placeholder numbers. `DATASET.md` is generated — edit the templates in
`scripts/write_dataset_doc.py`, not the output.

## Train the classifier

`app/data/classifier.joblib` is gitignored — it is a build artifact, not source.
Regenerate it before the API will start healthy:

```bash
python -m scripts.train_classifier                       # every CSV in app/data/
python -m scripts.train_classifier --data mydata.csv     # a specific dataset
python -m scripts.train_classifier --refresh-cache       # force GPT-2 re-extraction
```

**Features are cached.** The GPT-2 pass is the expensive part; the extracted
matrix is written to `app/data/features_cache.csv`, and later runs load it and
go straight to training. On the seed set that is 46s → 9s; on thousands of
essays it is the difference between a coffee break and a few seconds when you
just want to re-tune the classifier. The cache is validated against the current
`FEATURE_NAMES` and rejected with instructions if it is stale, so it can't
silently train on the wrong features.

Extraction is wrapped per essay: one empty, malformed, or unscoreable row is
counted and skipped rather than killing the run, and the reasons are tallied at
the end. A `tqdm` bar shows progress.

**Reported metrics come from 5-fold stratified cross-validation**, not one
80/20 split — a single split's accuracy can move several points on which essays
happen to land in the test fold. The script prints mean ± standard deviation
across folds, a pooled out-of-fold classification report, and **accuracy broken
out per `source`**. That last line is the one to read: blended accuracy is
dominated by whichever source has the most rows, and the `ai_polished` rows are
the hard cases. The final saved model is fit on the train split, with the
held-out score reported as a secondary check.

**Confusion matrices** are printed for both the pooled out-of-fold predictions
and the held-out split, with the two error cells labelled — a false positive
accuses a student who wrote their own essay, a false negative merely misses one,
and a bare 2×2 array is easy to read backwards.

**The fitted coefficients are printed at the end**, sorted by influence. This is
why the model is a logistic regression rather than something stronger and
opaque: because the features are standardised first, the weights are directly
comparable, and they are the same numbers `services/classifier.py` uses to
attribute an essay's score to individual signals. The explanation is the model,
not a story reconstructed afterwards. They are also saved to the artifact as
`feature_weights` so downstream code can read a name → weight mapping without
unwrapping the pipeline.

### Generate the evaluation report

```bash
python -m scripts.generate_evaluation      # -> EVALUATION.md
```

Reuses the saved model and `features_cache.csv` — no essay is re-scored through
GPT-2. Sections, in order: test-set metrics, cross-validated metrics, confusion
matrix, accuracy by source, the three highest-confidence failures, and the
ESL-bias discussion.

**Two sections need a human.** The explanation for each confident failure, and
the ESL-bias reasoning, sit between `<!-- MANUAL:... -->` markers. On every run
the script reads the existing `EVALUATION.md`, lifts whatever is inside those
markers, and puts it back — so retraining refreshes every number without
destroying the reasoning around them. The failure explanations are deliberately
left as a fill-in prompt: the point is to read the excerpt and think about it,
which a generated sentence would let you skip.

Class balance is printed immediately before training, with the majority-class
baseline when it is skewed — so the accuracy figure is read against the right
floor rather than against 50%.

Input CSVs need a `text` column and a binary `label` column (`1` = AI, `0` =
human). Training runs essays through the same `services/signals.py` code the API
uses, so training-time and inference-time feature vectors cannot drift apart.

`app/data/sample_essays.csv` is a 16-essay bootstrap set. It exists so the stack
runs end to end out of the box — it is **not** a training corpus, and a model
trained on it will not generalise. Replace it with real labelled data.

## Run

```bash
uvicorn app.main:app --reload --port 8000
```

Run it from the `backend/` directory so `app` is importable, or set
`PYTHONPATH=/path/to/backend`.

GPT-2 (~500MB) downloads on first run and is cached by HuggingFace thereafter.
Cold start is roughly 5s; after that both models stay resident and a typical
600-word essay scores in ~200ms.

## Endpoints

### `GET /health`

```json
{ "status": "ok", "model_loaded": true }
```

`model_loaded` reflects whether **both** GPT-2 and the classifier actually
loaded at startup, not merely that the process is answering. If either failed,
the service stays up and reports `false` so the failure is visible; `/analyze`
then returns 503.

### `POST /analyze`

```json
{ "essay": "..." }
```

Length is checked in two layers. Pydantic enforces `MIN_ESSAY_CHARS` (250) and
`MAX_ESSAY_CHARS`, which is cheap and rejects obvious junk before any work —
that returns **422**. The real limit is a word count enforced in the handler,
which returns **400** and reports the actual number:

```json
{ "error": "Essay is 20 words — at least 50 words are needed for reliable sentence-level analysis." }
```

An upper bound of `MAX_ESSAY_WORDS` (20,000) also returns 400: GPT-2 scoring
time grows with length, so an unbounded essay is an unbounded request.

**`/analyze` is rate limited** — `RATE_LIMIT_REQUESTS` per
`RATE_LIMIT_WINDOW_SECONDS` per client IP, returning 429 with a `Retry-After`
header. The counters are in-process, so with N uvicorn workers the aggregate
limit is roughly N times the configured one; it keeps one enthusiastic caller
from degrading a live demo rather than defending against a determined attacker.
Rejected requests are not recorded, so a blocked client's window still drains
instead of the limit becoming a ban.

Scoring failures return a generic `{"error": "Analysis failed — please try
again."}` with the real exception logged server-side via `logging.exception()`.
Specific failure modes (torch/OOM, tokenizer, feature lookup) are caught
individually so the logs say which; the caller sees the same message either
way.

Response:

```json
{
  "overall_probability": 0.0521,
  "confidence_label": "This essay's patterns align 95% with human-written examples in the training data.",
  "label": "Likely Human",
  "confidence": 0.896,
  "signals": { "perplexity": 45.1, "burstiness": -0.2955, "...": 0 },
  "sentences": [
    {
      "index": 0,
      "text": "...",
      "start_char": 0,
      "end_char": 75,
      "word_count": 14,
      "perplexity": 142.56,
      "mean_logprob": -4.96,
      "ai_likelihood": 0.018,
      "phrase": "resembles human-written examples",
      "flagged": false,
      "reasons": []
    }
  ],
  "flagged_sentence_count": 0,
  "top_features": [{ "name": "burstiness", "value": -0.29, "contribution": -0.38 }],
  "model_version": "20260815-074129",
  "processing_ms": 241.4

```

### Presenting the result

The output is a **likelihood, not a verdict**, and the API is built so a
frontend cannot easily present it as one:

- `overall_probability`, `confidence_label` and `label` are a set. Show all
  three together. A raw probability on its own is not a presentable result, and
  neither is the short tag.
- `confidence_label` is a complete sentence, already phrased as resemblance to
  training examples. Render it as-is rather than reformatting the number out of
  it.
- Every sentence carries a `phrase` as well as its `ai_likelihood`, so no
  per-sentence score is ever displayed as a bare number.
- `label` is a leaning — both values carry "Likely". The service never emits
  "definitely" or "detected", and never a bare percentage with no sentence
  around it.

`start_char`/`end_char` index into the essay after Unicode NFKC normalisation,
so a frontend can highlight flagged spans directly.

Every error response — 422, 503, 404, 500 — uses the same envelope:

```json
{ "error": "..." }
```

Unhandled exceptions are logged server-side with a full traceback and return
only `{"error": "Internal server error"}`; nothing internal reaches the client.

## Configuration

All configuration comes from the environment via `app/config.py`. No path,
origin, model name or threshold is hardcoded anywhere else. See `.env.example`
for the full annotated list; the two you will actually need to set:

- `CORS_ORIGIN` — comma-separated allowed origins, e.g.
  `http://localhost:5173,https://your-app.vercel.app`
- `MODEL_PATH` — path to the `.joblib`; relative paths resolve against
  `backend/`, not the shell's working directory

## Notes on the model pipeline

- **One forward pass per essay, not per sentence.** The essay is tokenised once
  and scored in overlapping 1024-token windows; per-sentence perplexity is then
  attributed by character offset. For a 600-word essay that is one pass instead
  of ~30.
- **Sentence splitting is regex-based, not NLTK punkt.** punkt needs a corpus
  download at runtime, which would make a fresh deploy fail on its first
  request.
- **The artifact owns the feature order.** `scripts/train_classifier.py` saves
  `feature_names` alongside the model, and `classifier.py` builds its input
  vector in *that* order, looking each feature up by name from the extracted
  signals. There is no second hardcoded list to drift out of sync: reordering
  `FEATURE_NAMES` in `signals.py` cannot silently misalign an existing model.
  What still fails loudly is an artifact trained on a feature `signals.py` no
  longer produces — that refuses to load rather than scoring nonsense.
